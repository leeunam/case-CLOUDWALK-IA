# F10 · Publicação temporária da demonstração

A demonstração reúne o frontend compilado no Caddy, Rails em production, PostgreSQL,
Kafka, worker, outbox e ponte do atendente simulado. A classificação usa a fixture
determinística do projeto. Use apenas dados sintéticos.

O [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/)
fornece HTTPS gratuito sem domínio ou conta. O endereço dura enquanto o processo e
o computador estiverem ligados, muda ao recriar o túnel e tem limite de 200
requisições simultâneas em voo. O serviço não oferece garantia de disponibilidade.
O ensaio histórico do projeto e a capacidade dessa demonstração têm condições e
objetivos diferentes.

## Preparar e verificar localmente

Use Docker local com Docker Compose v2.17 ou superior, BuildKit, Python 3.10 ou
superior em Linux/macOS e acesso aos registros das imagens. Reserve as portas de
loopback `18080` (sonda HTTP) e `18443` (HTTPS para verificar o fluxo local).
Caso estejam ocupadas, use `--http-port` e `--https-port` antes do comando e
repita as opções nas invocações da mesma instância.

Escolha um nome de projeto exclusivo com prefixo `cloudwalk_publish_` para
cada checkout novo ou nova instância. Antes de usar o nome, confira que ele
está livre, inclusive entre os volumes de instalações paradas. Os exemplos
usam `cloudwalk_publish_apresentacao`. Substitua pelo nome escolhido e passe
`--project "$projeto"` em toda a operação.

```sh
projeto=cloudwalk_publish_apresentacao
rtk proxy docker ps --all --filter "label=com.docker.compose.project=$projeto"
rtk proxy docker volume ls --filter "label=com.docker.compose.project=$projeto"
rtk proxy python3 -B script/publish.py --project "$projeto" init
rtk proxy python3 -B script/publish.py --project "$projeto" up
rtk proxy python3 -B script/publish.py --project "$projeto" check
rtk proxy python3 -B script/publish.py --project "$projeto" status
```

O primeiro `init` cria `.env.publish.local` com permissão `0600` e segredos
aleatórios. O arquivo fica fora do Git e `init` reaproveita o arquivo existente.
Anote o nome do projeto e guarde o arquivo privado desse checkout com os
três volumes da instalação. Mesmo após `down`, o nome ainda seleciona esses
volumes e o banco continua usando a senha do arquivo original. Para retomar
uma instalação, volte ao checkout e reuse o nome e o arquivo originais,
inclusive se a instalação original usava o nome `cloudwalk_publish`.

`up` aguarda o banco, as migrações, a criação dos tópicos e a saúde da API.
`db:prepare` inicializa os dados sintéticos em um banco novo e prepara os bancos
existentes nas atualizações. Caddy serve `/analista`, encaminha `/api`,
`/webhooks` e `/cable` ao Rails e impede que esses caminhos se confundam com as
páginas do frontend. O cookie usa `Secure`, `HttpOnly` e `SameSite=Lax`.
Somente as portas do Caddy ficam acessíveis no host e ambas são limitadas a
`127.0.0.1`. O Rails interpreta a conexão do proxy interno como HTTPS, inclusive
nas sondas e nos retornos assinados, com uma lista explícita de origens WebSocket.
[Configuração SSL do Rails](https://guides.rubyonrails.org/configuring.html#config-assume-ssl)
· [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)

O HTTPS local usa uma CA da própria instalação. Para testar no terminal, forneça
o certificado público a um cliente somente na chamada de teste.

```sh
ca=$(mktemp "${TMPDIR:-/tmp}/cloudwalk-publish-ca.XXXXXX")
rtk proxy python3 -B script/publish.py --project "$projeto" ca > "$ca"
rtk proxy curl --fail --cacert "$ca" https://127.0.0.1:18443/analista
rtk proxy python3 -B script/check_publish.py --project "$projeto"
```

O verificador confere as rotas, cache, autenticação, CSRF e upgrade WebSocket. Ele
envia um caso sintético assinado ao canal de chat da Aurora e imprime o ID do caso
e o ID de correlação quando vê o encaminhamento do mock. O caso permanece na
instância para a demonstração.

## Publicar e obter acesso

Execute `prepare` para validar a composição e baixar a imagem oficial do
cloudflared. Para abrir o endereço público explicitamente, execute `publish`.
Ele valida a URL temporária obtida do túnel, aplica o host e a origem HTTPS ao
proxy e ao Rails e imprime o endereço quando o HTTPS externo está pronto.
Uma falha nessa etapa aciona a parada do túnel e a recuperação da configuração local.

```sh
rtk proxy python3 -B script/publish.py --project "$projeto" prepare
rtk proxy python3 -B script/publish.py --project "$projeto" publish
rtk proxy python3 -B script/publish.py --project "$projeto" credentials
```

Leia as senhas sintéticas com `credentials` em um terminal privado. Abra a URL
HTTPS gerada, entre em `/analista` e use o acesso `bia@example.test` para acompanhar
um atendimento da Aurora. Compartilhe o acesso escolhido com o avaliador por
um canal privado. O frontend usa conexões de mesma origem para a API e o
WebSocket. Reiniciar o processo do túnel exige confirmar o endereço atualizado
com `publish`. O Compose mantém o túnel desligado no `up` e no `check`.

## Parar, recuperar e atualizar

```sh
rtk proxy python3 -B script/publish.py --project "$projeto" unpublish
rtk proxy python3 -B script/publish.py --project "$projeto" logs
rtk proxy python3 -B script/publish.py --project "$projeto" down
```

`unpublish` encerra o túnel e mantém o ambiente local disponível. `down` para e
remove os contêineres do projeto e preserva os volumes do banco, Kafka e Caddy.
Para retomar, execute `up` e `check` com o mesmo projeto, portas e arquivo
privado. Em caso de falha, consulte `status` e `logs` para identificar o serviço.
Para atualizar, pare a publicação, faça a cópia dos volumes e da configuração
privada, atualize o checkout e repita `up` e `check` antes de publicar novamente.

### Parada de emergência do túnel

Se o arquivo privado estiver ausente ou com permissões inválidas, use o Docker
diretamente para interromper a publicação. Informe em `projeto` o nome exato
usado ao publicar e confira o ID, o nome e as duas etiquetas do contêiner.

```sh
projeto=cloudwalk_publish_apresentacao
rtk proxy docker ps --no-trunc \
  --filter "label=com.docker.compose.project=$projeto" \
  --filter 'label=com.docker.compose.service=cloudflared' \
  --format '{{.ID}} {{.Names}} {{.Label "com.docker.compose.project"}} {{.Label "com.docker.compose.service"}}'
```

Na mesma sessão do terminal, substitua `ID_CONFIRMADO` pelo ID completo exibido.
O comando confere novamente o ID e as etiquetas antes de parar o contêiner.

```sh
id=ID_CONFIRMADO
if [ -n "$id" ] && [ "$(rtk proxy docker ps --no-trunc \
  --filter "id=$id" \
  --filter "label=com.docker.compose.project=$projeto" \
  --filter 'label=com.docker.compose.service=cloudflared' \
  --format '{{.ID}}')" = "$id" ]
then
  rtk proxy docker stop "$id"
else
  printf '%s\n' 'Parada cancelada. Confira o projeto e o ID exibidos.'
fi
```

Só o túnel é interrompido. A aplicação local, os dados e a configuração do host
na API e no Caddy permanecem. Para restaurar a configuração local, recupere o
arquivo privado original com permissão `0600` e execute
`rtk proxy python3 -B script/publish.py --project "$projeto" unpublish` no
checkout da instalação. Depois, use `check` com o mesmo projeto.

### Cópia offline e restauração

Pare a pilha com `down` antes de copiar os volumes para preservar um ponto
consistente. Use o projeto original em `$projeto` e guarde seu nome junto à
cópia. Os comandos usam a mesma imagem PostgreSQL do Compose como ferramenta de
cópia. A pasta e os arquivos ficam privados, incluindo a chave da CA local no
volume do Caddy.

```sh
umask 077
backup=$(mktemp -d "${TMPDIR:-/tmp}/cloudwalk-publish-backup.XXXXXX")
imagem=postgres:17-alpine@sha256:a77aa70e641402a21411b92b721c58d10f23b50ae5fdd2333efd22d166e1e5f7
rtk proxy cp .env.publish.local "$backup/.env.publish.local"
for volume in postgres_data kafka_data caddy_data
do
  rtk proxy docker run --rm --network none --entrypoint tar \
    --mount "type=volume,src=${projeto}_$volume,dst=/data,readonly" \
    "$imagem" -C /data -czf - . > "$backup/$volume.tar.gz"
done
```

Guarde a pasta em local privado, junto ao commit que produziu a cópia. Para
testar a restauração, use um checkout nesse commit, uma configuração privada
copiada desse backup com permissão `0600` e um nome de projeto novo. Confirme
com `docker volume ls` que os três nomes de destino estão livres. Preserve as
versões do banco e do Kafka e as permissões internas dos volumes.

```sh
restauracao=cloudwalk_publish_recuperacao
for volume in postgres_data kafka_data caddy_data
do
  rtk docker volume create --label "com.docker.compose.project=$restauracao" \
    --label "com.docker.compose.volume=$volume" "${restauracao}_$volume"
  rtk proxy docker run --rm -i --network none --entrypoint tar \
    --mount "type=volume,src=${restauracao}_$volume,dst=/data" \
    "$imagem" -C /data -xzf - < "$backup/$volume.tar.gz"
done
rtk proxy python3 -B script/publish.py --project "$restauracao" up
rtk proxy python3 -B script/publish.py --project "$restauracao" check
```

### Exercício de persistência

1. Execute `script/check_publish.py` pelo Python com a pilha pronta. Guarde o ID
   que aparece ao lado da mensagem de encaminhamento.
2. Execute `down` e `up` no mesmo projeto.
3. Execute `rtk proxy python3 -B script/check_publish.py --project "$projeto" --case-id ID_DO_CASO`.
   Confira o mesmo ID, o relato original e o encaminhamento do mock. Em uma
   publicação, refaça a verificação na URL HTTPS a partir de outra rede.
