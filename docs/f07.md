## Execução

Na worktree, com Python 3.11+, Docker Engine acessível e Docker Compose com suporte a `!reset` e BuildKit:

```bash
cd /home/inteli/Documents/projetos/case-CLOUDWALK-IA/.worktrees/integracao-f06-f07
rtk proxy python3 -B script/f07/run.py --check-config
rtk proxy python3 -B -m unittest discover -s script/f07 -p 'test_*.py' -v
rtk proxy python3 -B script/f07/run.py > /tmp/cloudwalk-f07-a-report.json
```

Para reproduzir uma falha individual, use `--scenario 01` a `--scenario 05`. A opção aceita múltiplas ocorrências.

```bash
rtk proxy python3 -B script/f07/run.py --scenario 05 > /tmp/cloudwalk-f07-a-offsets.json
```

O runner envia o JSON a stdout e os diagnósticos a stderr. Código `0` indica que todos os cenários selecionados foram aprovados, `1` indica ao menos uma divergência observada e `2` indica integração bloqueada, erro de execução ou erro de limpeza. Ausência de uma condição observável dentro da janela gera `bloqueado`. Os horários da janela de teste servem para diagnóstico, sem representar SLA. A evidência parcial permanece no JSON.

## Pilha e observações

O projeto Compose `cloudwalk_f07_a` exige rede, contêineres e volumes próprios vazios. O override remove as portas publicadas da API e do frontend e usa uma rede interna. O runner recusa uma pilha preexistente e, quando inicia uma, remove somente os recursos do seu projeto ao terminar. Rails, PostgreSQL, Kafka, ponte, outbox, mock e worker usam os componentes do produto. O ensaio usa processos Rails distintos para o WebSocket e para a escrita e executa o cliente TypeScript do simulador com HTTP e cookies reais em Node. Os segredos são sintéticos e gerados por execução, com o Jev em modo fixture.

O writer monta os contratos em modo somente leitura. O outbox e o writer aguardam o preparo do banco. O verificador exige contêineres do worker e do outbox em execução e conexões de ambos aos bancos correspondentes. Ele espera HTTP acessível, tópicos com líderes, grupos estáveis com as três partições atribuídas e, no replay, o grupo sem membros antes de alterar o offset. As leituras de Kafka observam intervalos delimitados pelo início e pelo fim do log sem gravar offsets. O observador SQL abre transações somente para leitura. O JSON registra correladores, contagens, auditoria, recibos, hashes dos corpos examinados e coordenadas Kafka. `committed_next_offset` indica a próxima posição que o grupo deve consumir.

### O que os controles observam

No cenário 04, cada uma das três correções muda a categoria e a versão do mesmo atendimento. O verificador lê a auditoria no PostgreSQL e recebe um aviso do caso no socket do supervisor após cada escrita. O socket do simulador permanece inscrito desde antes do logout. O verificador consome os frames acumulados e observa mais seis segundos após o último controle. Um aviso na assinatura antiga reprova o cenário. O JSON distingue um fechamento normal de uma janela concluída sem aviso e informa o tempo observado. O resultado de ausência vale para essa janela.

No cenário 05, somente a ponte de retornos usa o listener Kafka `F07`. O broker anuncia o endereço de um proxy interno nesse listener. O único tópico produzido por essa ponte é `agent.failures`. O proxy lê a chave da API e o identificador de correlação do cabeçalho em cada conexão. Quando o probe arma o controle, o proxy retém a resposta real ao próximo `Produce`. Os pedidos `OffsetCommit` continuam trafegando e são contados dos dois lados da liberação. O probe consulta o broker diretamente pelo listener habitual. [Protocolo Kafka 4.4](https://kafka.apache.org/44/design/protocol/)

Durante a retenção, o fim do log de falhas deve avançar uma posição e o offset do grupo deve continuar apontando para o registro de entrada. O probe só então libera o ACK. O cenário exige um único Produce e um único commit posterior na ponte durante o controle. A posição adicionada a `agent.failures` deve conter os IDs e a origem exata do caso. Se a janela de 1,2 s expirar, o proxy encaminha os bytes e o ensaio perde a medição. Esse teto fica abaixo do timeout de publicação de 1,5 s configurado no produto.

O runner aceita até 240 s de inatividade entre mensagens completas do probe e até 300 s de preparação mais 600 s por cenário selecionado para a sessão de verificação. Comandos Docker em andamento têm timeout próprio. Após o encerramento por prazo, o runner aguarda até cinco segundos pelo término normal do processo e até cinco segundos após forçar sua saída.

## Verificações e pendências

A matriz registra a execução real do integrador em `fbc2192`, com os cinco
cenários aprovados e limpeza concluída. O [JSON completo](evidencias/f07-a-2026-11-20.json)
inclui a revisão efetiva, correladores, offsets e as pós-condições. Uma rodada
anterior em `c7239cd` também aprovou os cinco cenários. Passaram a validação
do Compose e os 12 testes isolados do harness. A análise estática Python e a
verificação de sintaxe Python e JavaScript passaram na revisão do harness.

A primeira execução em `c3aa4ea` reproduziu uma chamada inexistente do SDK e
a ausência do schema no writer. A revisão também exigiu um controle causal
do ACK e controles de escrita para a janela de revogação. As correções em
`c7239cd` resolveram esses pontos antes do aceite. O limite de inatividade do
runner ainda pode encerrar uma preparação excepcionalmente lenta; isso gera
diagnóstico de bloqueio, sem contar como aprovação.

A F07-A cobre os fluxos F02–F05 sobre o código integrado da F06. Os testes
de configuração, migração e as corridas administrativas da F06 estão na
[integração conjunta](integracao-f06-f07.md). Carga, avaliação real do Jev e
publicação pertencem às entregas seguintes.
