## Alterações

1. O supervisor cria uma fila e seleciona equipes autorizadas da marca.
   Uma regra ativa tem prioridade, categoria ou ambos como filtro e a menor
   posição compatível vence. A mesma seleção vale para entrada classificada
   no canal, complemento Jev e correção inicial. O atendimento registra a
   fila, a regra e sua versão na auditoria. Alterar uma regra afeta os
   próximos encaminhamentos. O atendimento em curso conserva a fila.
2. A supervisão edita marcas existentes, autorizações, fila padrão, equipes e
   membros. A API recusa vínculos de outra marca, fila ativa sem equipe,
   desativação com casos ou regras ativas e alterações em equipe compartilhada
   fora do escopo. A revogação de acesso reconcilia responsáveis antes do
   commit. Casos aguardando cliente mantêm a espera, agora sem responsável.
3. O catálogo aceita categorias da operação e mantém os quatro códigos de
   prioridade. A API valida as dependências e o limite de opções do Jev.
   O simulador usa o catálogo ativo do canal. A caixa e a supervisão recebem
   também os nomes históricos. Os perfis publicam novas versões, aceitam
   alternativas de pares prioridade/categoria e verificam duplicatas e teto.
   Reduzir um perfil preserva o trabalho ativo e aplica a nova configuração à
   elegibilidade futura.
4. A caixa da supervisão filtra casos em revisão e falhas da IA. Correção com
   motivo, transferência e ações `retry_agent` e `force_handoff` usam os
   comandos canônicos com versão e idempotência. A auditoria do atendimento
   mostra o encaminhamento inicial. A auditoria administrativa tem paginação,
   filtros de recurso na API e existe independentemente de atendimentos.

A publicação administrativa usa o protocolo de bloqueios da operação. As
marcas são adquiridas por UUID antes de revalidar autorização e versão. Quando
há revogação, usuários e atendimentos seguem na mesma ordem de precedência e
por UUID dentro de cada conjunto. A trava de todas as marcas simplifica o
escopo de edições compartilhadas, com o custo de serializar temporariamente
publicações administrativas independentes. A auditoria compartilha a
transação e uma correlação une os registros de uma alteração multimarca.
A auditoria de perfil usa o ID do usuário como ID do recurso ao longo das
versões e inclui os pares de categorias visíveis no catálogo da marca
consultada. A consulta e a publicação do perfil vigente exigem autorização
sobre todos os vínculos atuais do analista e todas as categorias do perfil.
Uma chave precisa estar ativa em alguma marca supervisionada ou constar
exclusivamente no histórico das marcas supervisionadas. A API responde com
`403` quando um vínculo removido deixa categorias fora desse escopo. Os pares
guardam a chave da categoria. Quando uma chave inativa no escopo também existe
no catálogo de uma marca externa, a supervisão precisa abranger as marcas da
chave para consultar o perfil e atualizá-lo para o catálogo ativo atual.
Cada nova versão da auditoria conserva a projeção por marca apurada no
momento da publicação. A adoção posterior de uma chave preserva a projeção
dos eventos anteriores. Para registros antigos sem confirmação desse escopo,
a consulta omite `alternatives` e conserva os demais campos do histórico.

As ações da conversa registram a versão do atendimento ao iniciar o rascunho.
Se outra operação alterar o caso, a supervisão pode descartar o rascunho e
revisar o estado atualizado. Durante um envio ou enquanto sua confirmação
está pendente, os demais comandos ficam indisponíveis. A confirmação repete
o corpo, a versão e a chave originais. O botão **Preparar outra ação** permite
abandonar a tentativa pendente explicitamente.

No contrato, categorias em canais e filtros, escopo de analistas, membros
de equipe e dados de roteamento na auditoria são campos aditivos. A API de
vínculos publica as versões afetadas. Um `POST /api/v1/teams` com apenas o
nome vincula a equipe às marcas supervisionadas pelo ator. A interface
informa a marca inicial explicitamente. A remoção do último vínculo mantém
a equipe disponível à administração da marca que a desvinculou.

## Reprodução

Execute na worktree F06, com Docker disponível. Use o projeto isolado
`cloudwalk_f06_dev` e confirme disponibilidade das portas 3106 e 5176.
Prepare e execute os testes antes de iniciar a sessão de desenvolvimento.

```bash
rtk docker compose -p cloudwalk_f06_dev up --build -d db_setup kafka_setup
rtk docker compose -p cloudwalk_f06_dev wait db_setup kafka_setup
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps -e RAILS_ENV=test db_setup bundle exec rails db:prepare
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps -e RAILS_ENV=test db_setup bundle exec rails test
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps db_setup bundle exec rails zeitwerk:check
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps db_setup bundle exec ruby /workspace/script/check_contracts.rb
rtk docker compose -p cloudwalk_f06_dev build web
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps web npm test
rtk docker compose -p cloudwalk_f06_dev run --rm --no-deps web npm run build
```

A imagem web instala com `npm ci`. Para a sessão interativa, informe
`CLOUDWALK_DEMO_PASSWORDS` no ambiente com as credenciais sintéticas locais
do supervisor e dos analistas que serão usados. O login de supervisão usa
`supervisor@example.test`.

```bash
export API_PORT=3106 WEB_PORT=5176 CLOUDWALK_JEV_MODE=fixture
rtk docker compose -p cloudwalk_f06_dev run --no-deps -d --service-ports --use-aliases \
  --name cloudwalk-f06-api -e CLOUDWALK_DEMO_PASSWORDS api
rtk docker compose -p cloudwalk_f06_dev up -d --no-deps worker web
```

1. Abra `http://127.0.0.1:5176/` e envie um atendimento Pix com
   prioridade básica na Aurora. Na operação, em `/analista`, confirme que
   esse caso começou na fila padrão.
2. Com o supervisor, abra **Configuração operacional → Filas** para Aurora.
   Crie **Triagem Pix** com **Suporte compartilhado** e **Especialistas
   Aurora**. Em **Regras**, publique uma regra ativa de categoria Pix com
   posição 10 para a nova fila.
3. No simulador, abra outra conversa Pix na Aurora. Na caixa, consulte ambos
   os casos e compare as filas. Abra **Auditoria do atendimento** e confira a
   regra publicada no caso novo. Em **Auditoria**, confira os registros
   administrativos da fila e da regra.
4. Em **Catálogo**, publique uma categoria da Aurora e recarregue o
   simulador para conferir o seletor. Em **Perfis**, publique uma alternativa
   para Bia com o par nova categoria/prioridade e teto compatível.
5. Com Jev em modo fixture, envie de outro atendimento um relato vago com
   categoria omitida. Consulte **Em revisão** e aplique uma correção com
   motivo. Para testar recuperação e transferências com a ponte, use a
   preparação de mensageria do [roteiro F03](f03.md), com os nomes, rede e
   portas do projeto F06. No caso com falha da IA, use **Falhas da IA** para
   tentar novamente ou encaminhar a um humano. Depois use **Transferir
   atendimento** e confira a trilha.

## Exercício curto

Publique duas regras de Pix com filas diferentes e posições 10 e 20. Abra um
caso antes da alteração, desative a regra de posição 10 e abra outro. Compare
as duas filas e as versões registradas nas auditorias. A diferença mostra
quando o roteamento é decidido e como o histórico preserva essa decisão.
