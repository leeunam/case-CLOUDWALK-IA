# F05 · Preparação da interface com fixtures

Etapa inicial integrada em 2026-11-19 sobre a base `c691b6a`, junto da F02.
O simulador React usa dados sintéticos no armazenamento do navegador.
A API real, a sessão do simulador, o WebSocket e a caixa do analista ainda
precisam ser integrados; esta entrega não conclui toda a F05.

## Comportamento verificado

- Chat, WhatsApp e e-mail usam o catálogo e os formatos dos contratos v1.
- A conversa recupera canal, identidade externa e histórico. Uma nova
  solicitação após a resolução abre outro caso ligado ao anterior.
- O adaptador mantém uma rodada pendente por caso e conserva a sequência
  considerada. Relatos posteriores entram na próxima rodada antes da resolução.
- Detalhe e mensagens são lidos do mesmo estado local. A resposta final e o
  estado resolvido aparecem juntos.
- Um envio de novo atendimento bloqueia marca, canal e navegação no histórico.
  Se falhar, os controles voltam e o rascunho permanece.
- Ao reconectar, catálogo, histórico e conversa são consultados novamente.
  O caso aberto é preservado e o chat retoma as consultas periódicas.
  Uma falha de catálogo também oferece repetição sem sair da conversa.

## Verificações executadas

Ambiente: Node 22.23.5 da imagem fixada no Dockerfile, React 19.3.1 e Vite 8.3.8.

- A instalação pelo lockfile e o build TypeScript/Vite passaram no Docker.
- Os seis testes de `frontend/test/fixtureRepository.test.mjs` passaram.
  Cobrem rodadas, relatos pendentes, resolução, recuperação de dados antigos,
  reentrega, conflito de chave e abertura vinculada nos três canais.
- No navegador, o integrador verificou criação, resposta, bloqueio dos seletores,
  histórico de WhatsApp resolvido com quatro mensagens e recuperação após
  recarregar a mesma URL.
- Três cenários adicionais passaram no Chrome sem interface com a fonte final
  compilada: perda de conexão nas consultas iniciais seguida de recuperação
  do catálogo, histórico, envio e polling no mesmo caso; repetição manual
  quando o evento `online` não chega; e bloqueio da navegação durante envio
  suspenso com reativação e rascunho preservado após erro.

O ensaio de navegador adicional foi executado com um harness temporário do
ambiente de integração. Ele não faz parte do `npm test`; os cenários abaixo
permitem repetir manualmente as verificações. Uma suíte de navegador portátil
continua como trabalho de verificação das próximas etapas.

## Reproduzir e aprender

Na raiz do repositório, suba o ambiente conforme o README. Para executar
as regressões no Node fixado do projeto:

```sh
rtk docker compose run --rm --no-deps web npm test
rtk docker compose run --rm --no-deps web npm run build
```

No simulador em `http://localhost:5173/`:

1. Selecione WhatsApp, use o exemplo e envie. Confira o bloqueio dos seletores
   e, depois, a marca e o canal da conversa.
2. Atualize até receber a primeira resposta e envie dois complementos rápidos.
   Atualize para acompanhar as rodadas. A resolução deve considerar os relatos
   pendentes e aparecer junto da resposta final.
3. Recarregue a URL e confira que o mesmo caso e as mensagens permanecem.
4. Com a aplicação carregada, simule uma perda de conexão antes de as consultas
   iniciais terminarem. Reconecte e confira que marca, canal e campo de resposta
   voltam no mesmo caso. No Chat, envie um complemento e confira a atualização.
5. Use `/?fixture=empty` e `/?fixture=error` para observar o estado vazio e a
   repetição da leitura de histórico após erro.

Exercício: siga o envio de `Composer.tsx` para `fixtureRepository.ts`. Localize
a chave de idempotência e a sequência coberta pela rodada. Explique por que
repetir a mesma tentativa conserva o recibo e não acrescenta outra mensagem.

## Pendências para a API real

- Implementar o adaptador de sessão, catálogo, consultas e envio com CSRF.
- Definir a origem autorizada dos nomes das marcas: o catálogo de canais atual
  contém `brand_id`; a listagem de marcas é restrita à supervisão. As fixtures
  contêm nomes sintéticos, sem ampliar permissões do contrato.
- Conectar atualização e reconexão por WebSocket, caixa do analista e ações
  humanas às etapas F02–F04; validar as permissões no servidor.

As fixtures não medem latência de atendimento, capacidade nem segurança da API.
