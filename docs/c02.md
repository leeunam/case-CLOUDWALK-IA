# C02 · Avaliador comum de classificação

O [relatório de demonstração](../script/classification_comparison/example/report.md) reúne 24 relatos de desenvolvimento e 12 controles. A fixture completou 3 dos 17 relatos inteiramente classificáveis e preservou os 25 campos válidos recebidos, incluindo controles. Quatro controles completos ou inválidos passaram pelo avaliador com zero chamadas. As 32 tentativas produziram 33 requisições simuladas e 43 perguntas. O custo de API e os percentis de inferência ficaram sem medição. A elegibilidade da fixture é sempre `inconclusive`.

## Reprodução

Na raiz da worktree, use Python 3.11+, Git e as dependências de [requirements.txt](../script/classification_comparison/requirements.txt). A suíte de interoperabilidade também usa Ruby. Cada comando de execução requer um diretório de saída novo dentro do checkout para que os caminhos e os hashes sejam verificáveis. Os comandos abaixo funcionam sem rede, credenciais ou modelo instalado.

```sh
rtk proxy python3 -B script/classification_comparison/run.py --dry-run --limit 3 --output script/classification_comparison/preparo
rtk proxy python3 -B script/classification_comparison/run.py --output script/classification_comparison/lote
rtk proxy python3 -B script/classification_comparison/test_evaluator.py -v
rtk proxy python3 -B script/check_classification_contracts.py
rtk proxy python3 -B docs/planejamento/classificacao-comparativa/contratos/test_regressions.py -v
```

O dry run valida os schemas e seus vínculos, os hashes das fontes e dos controles, a compatibilidade das versões, as máscaras e a partição completa. Ele produz `plan.json`, a invocação e o fluxo de inputs, sem iniciar o subprocesso. `--limit N` seleciona os primeiros N relatos na ordem do manifesto da partição. Os 12 controles são adicionais e oito deles exercitam o adaptador. Use `--split control` para executar apenas esses controles. As flags `--concurrency 1` e `--attempts 1` refletem os limites congelados. Sem flags, o lote usa fixture e desenvolvimento. A opção `--split final_test` permite testar a mecânica dos denominadores com dados simulados. Uma amostra limitada dessa partição conserva os 36 IDs no plano.

## Integração Ruby ou Python

Use [fixture.json](../script/classification_comparison/fixture.json) como exemplo para `--config caminho.json`. Declare o vetor `command`, a identidade congelada e as referências de prompt e política com caminho relativo à raiz, versão e SHA-256. A identidade informa modo, fornecedor, modelo solicitado, versões do adaptador e da política e eventuais versões esperadas de modelo ou pesos. O runner verifica a configuração antes de iniciar o comando. A opção explícita `--mode real` exige uma identidade real. O piloto e a execução final de candidatos dependem da autorização e do orçamento do integrador.

1. O runner inicia **um processo por lote**, com diretório de trabalho na raiz. Ele entrega `CLASSIFICATION_RUN_ID`, `CLASSIFICATION_IDENTITY` (JSON), `CLASSIFICATION_TIMEOUT_MS` e os caminhos `CLASSIFICATION_RUBRIC`, `CLASSIFICATION_PROMPT` e `CLASSIFICATION_POLICY`. Após carregar recursos e aquecer o motor, o adaptador publica por rename atômico um JSON em `CLASSIFICATION_READY_FILE`, com strings `runtime` e `hardware`. Pode incluir `seed`, `peak_memory_bytes` e `infrastructure_usd` quando já conhecidos. O avaliador mede o tempo de inicialização até essa sinalização.
2. Para cada entrada apta, o processo lê do stdin uma linha UTF-8 do schema de input. Recebe somente ID, texto, marca, catálogo, campos do canal, máscara e versão de contrato. Ruby pode usar `STDIN.each_line` e Python pode iterar sobre `sys.stdin.buffer`. A fronteira do registro é LF. U+2028, U+2029 e U+0085 dentro do texto pertencem ao mesmo registro.
3. O adaptador emite no stdout uma linha do schema de observação e faz flush. Inclui o mesmo ID, run, identidade, tentativa 1 e uma escolha por campo omitido. Registra timeout, erro operacional, saída faltante e divergência de versão conforme a C01. A emissão de erro inclui a evidência já obtida de outros campos e uma linha de usage para cada requisição enviada. O prazo de inferência é de 5 s por relato. O transporte admite até 250 ms adicionais para entregar uma observação de timeout. EOF de stdin encerra o adaptador. Diagnósticos vão ao stderr.
4. O avaliador valida cada resposta, aplica a regra tudo-ou-revisão e verifica a decisão com o checker da C01. Em caso de protocolo quebrado, ID divergente, morte ou silêncio do processo, a CLI termina com código 2. Os fluxos escritos conservam o prefixo validado. Somente um lote verificado gera `report.json`. O adaptador deve registrar falhas operacionais como observações válidas para incluí-las nas métricas, inclusive quando conhece zero requests enviados.

## Artefatos e denominadores

| Arquivo | Uso |
| --- | --- |
| `invocation.json` | Comando de reprodução com diretório novo, hash da configuração e limites. |
| `inputs.jsonl` | Entradas portáteis na ordem do plano, seguidas dos controles. Inclui as entradas bloqueadas antes do adaptador. |
| `observations.jsonl` | Evidência por tentativa, com escolhas brutas, erros, modelo e usage por requisição. |
| `decisions.jsonl` | Uma linha por caso, inclusive com zero tentativas, com valores aplicados e motivo de revisão ou conclusão. |
| `report.json` e `report.md` | Manifesto conforme o schema e leitura das métricas por campo, máscara e estrato. O JSON inclui hashes, estados de medição, ambiente e inventário dos fluxos. |

O acerto bruto usa todos os campos omitidos da fatia. Abstenção explícita ou por política acerta quando o gabarito pede insuficiência. O acerto aplicado divide os códigos corretos pelos campos-alvo efetivamente aplicados. A revisão usa relatos como denominador. A cobertura automática usa relatos inteiramente classificáveis e a cobertura correta exige também todos os códigos certos. Os controles entram nos indicadores de integridade e uso. As fatias de qualidade e urgência usam somente os relatos da partição.

Nos urgentes, uma escolha bruta `urgent` pode coexistir com revisão causada pela categoria. Um rebaixamento automático exige que uma prioridade inferior tenha sido aplicada. O relatório conserva as duas medidas. Em execução real, os percentis usam posto mais próximo sobre tentativas aquecidas, inclusive falhas com duração medida. Tokens e custos somam cada requisição uma vez. Uma de duas requisições com cobrança conhecida produz total parcial com uma amostra observada. Medições ausentes usam valor nulo, enquanto contadores conhecidos preservam zero.

A referência é sintética e exploratória. O responsável revisou diretamente oito dos 60 relatos e delegou a revisão dos demais 52 à IA. O resultado de demonstração descreve a fixture e o caminho de avaliação. A comparação de qualidade e latência entre candidatos depende de medições reais.
